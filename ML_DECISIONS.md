**ML pipeline**

| Part | Final setting |
|---|---|
| Inputs (ego-only) | camera + last 2–3 frames, LiDAR BEV + last 2–3 sweeps, own speed / accel / yaw rate / steer, **route command (left / straight / right / U-turn)**; no goal point, no behaviour tag, nothing about other vehicles |
| Encoders | SegFormer-B0 (Cityscapes) and PointPillars (nuScenes), heads removed, **frozen**, features cached. **One LiDAR encoder only (PointPillars)**; ResNet-18 BEV is a fallback, used only if PointPillars can't be installed or its frozen features clearly don't work on CARLA LiDAR |
| Trained layers | state MLP, fusion MLP (→ 512), GRU decoder |
| Outputs | 6 trajectories × 10 waypoints + scores (winner-takes-all); behaviour head (output only) |
| Control | PID at 20 Hz in CARLA |
| Training | stage 1 frozen encoders; stage 2 unfreeze last encoder stage at 10× lower LR only if validation improves; manoeuvre samples over-weighted 3–5× |
| Ablations | no route info |
| Evaluation | open-loop minADE/FDE; closed-loop CARLA on held-out pairs: collisions, kerb hits, progress, style metrics vs real Gwalior data; baselines expert replay, CARLA Autopilot, old SegFormer BC |

## 3. Surrounding vehicles

| # | Decision | Status |
|---|---|---|
| S1 | Each scenario spawns the 2 behaviour vehicles (ego + other; U-turn has 1) **plus up to 4 surrounding vehicles**: `min(vehicles within 30 m, 4 nearest)`. Pedestrians are never spawned. | Decided |
| S2 | Clearance rule: candidates are added nearest-first; a candidate is accepted only if its CARLA body stays **≥ 0.5 m** from every vehicle already accepted (including the shifted ego/other paths) for the whole window, it can be spawned, and it stays on the drivable area. Otherwise skip it and try the next nearest. Fewer than 4 is allowed. | Decided (X = 0.5 m, chosen by Claude at Raj's request) |
| S3 | Why 0.5 m, not 0.3 or 0.7: 0.3 m is the current warning level and too tight (CARLA Micra is wider than Gwalior cars); 0.7 m would drop many real neighbours and remove the close passing that is the Gwalior style. **The builder reports how many neighbours would be dropped at 0.3 / 0.5 / 0.7 m**; if 0.7 loses little, switch to 0.7. | Decided |
| S4 | Record per scenario how many real neighbours were dropped by the clearance rule (the real driver may have reacted to a vehicle that is no longer there). | Decided |

## 4. Augmentation

| # | Decision | Status |
|---|---|---|
| A1 | **10 augmented copies per scenario: 5 + 5.** **RHD (2026-11-10): 3 scene noise + 4 ego offset + 3 ego speed recovery** (section 0a). | Decided |
| A2 | 5 copies — **smooth scene noise**: slowly varying whole-path sideways offset (σ ≈ 0.2–0.3 m), speed scaled ±5–10 %, start time shifted up to 0.5 s. (Whole-scene rotation dropped 2026-10-25.) Values are first guesses; keep them near the tracking-noise size. | Decided |
| A3 | 5 copies — **ego start perturbation**: ego rendered 0.5–1 m off its path or turned 5–10°; label = waypoints that return to the real path (fixes closed-loop drift / covariate shift). | Decided |
| A4 | **Not allowed:** independent Gaussian noise on every point (jittery, physically impossible paths), and noise on the ego's target/label path (teaches random paths as "expert"). | Decided |
| A5 | Every augmented copy is re-checked: behaviour type unchanged (overtake still behind→ahead, cut-in still crosses the lane, …), gap ≥ 0.5 m to all vehicles, on the drivable area. Failures are regenerated or dropped. | Decided |
| A6 | Augmented copies of one pair always stay on the same side of the train/test split. | Decided |

## 5. Model inputs and outputs

| # | Decision | Status |
|---|---|---|
| M1 | **Ego-only inputs**, as a real car would have: front camera, LiDAR, own speed, acceleration, yaw rate (IMU), current steering angle, route goal. **No speeds/positions/trajectories of other vehicles** as input. Others are perceived only through camera + LiDAR. | Decided |
| M2 | The ego's **own** past (odometry/IMU history) is allowed. Its own last 2–3 sensor frames (stacked LiDAR BEV or previous camera features) are allowed, so it can perceive other vehicles' motion. | Proposed |
| M3 | **No behaviour tag as input — dropped completely.** Reasons: nobody can set it while driving; it is derived from the future (leaks the answer); the model would obey the tag instead of reading the scene. | Decided |
| M4 | Behaviour type is used as an **extra output head** (the model predicts which behaviour it is doing) and for sample weighting/reporting. | Proposed |
| M5 | Route command (left / straight / right / U-turn at the junction) as input is allowed, since a navigation system gives it. **Goal** = one (x, y) point in the car's own frame, on the path the real vehicle actually drove, ~20–30 m ahead of it (like the next GPS waypoint); it says where to go, not when to arrive or how to drive. It is an **input**, recomputed at every planning step (it slides forward along the route as the car moves); near the end of the track it is the last track point. **Not** the expert's exact position at a fixed future time (that would leak timing/speed). At test time it comes from a route planner to the scenario's destination. **Reopened 2026-10-23: Raj dislikes any future-derived input.** Options: (a) no route info at all (free driver; can't choose a junction exit, U-turns rarely happen), (b) route command only (left/straight/right/U-turn, no coordinates), (c) goal point. Since encoder features are cached, train with and without as an ablation. **Decided 2026-10-23: option (b), route command only** (4-way one-hot: left / straight / right / U-turn at the next junction), **no goal point, no coordinates**. Option (a) (no route info) trained as an ablation. | Decided |
| M6 | Output: future waypoints (Raj's diagram: 10 × 0.25 s = 2.5 s), tracked by PID in CARLA. Labels resampled from 4.27 fps to 0.25 s by interpolation. Multiple trajectories + scores (K = 3–6, winner-takes-all) instead of a single one, so left/right/follow are not averaged. **Now 1 mode** (6 modes tied 1 mode in the 2026-10-29 sweep; RHD runs use 1, section 0a). | Decided |
| M7 | Architecture: Raj's diagram (SegFormer-B0 camera branch, ResNet-18 LiDAR BEV branch, goal MLP, concat fusion → GRU waypoint decoder → PID) with the fixes above. Control rate: run at 20 Hz (PID gains in `scc.py` assume dt = 0.05) or retune for 50 Hz. Render the camera directly at 256×256 (or 512). | Proposed |

| M10 | **Vehicle type as input**: 5-way one-hot of the CARLA blueprint (Micra, Ninja, Microlino, Sprinter, T2) concatenated with state + route command into the state MLP. Lets bike samples (50 %, different camera height/view) be used without biasing the car policy; at test time it is the blueprint actually spawned. Closed-loop eval runs on all 5 types (Micra main), reported per type. Chosen over "use all as is" and "weight cars up". | Decided (2026-10-27) |
| M8 | Pretrained encoders: camera = SegFormer-B0 encoder (Cityscapes-finetuned `nvidia/segformer-b0-finetuned-cityscapes-1024-1024`). LiDAR = **PointPillars/CenterPoint backbone pretrained on nuScenes** (32-beam, closest to CARLA's 32-ch), detection head removed, BEV feature map used. ResNet-18 BEV only as a fallback (decided 2026-10-24). Needs OpenPCDet or mmdetection3d installed (ask Raj before installing). | Proposed |
| M9 | Fine-tuning: drop the pretrained models' task heads (class/detection layers). Stage 1: freeze both encoders, cache their features once, train fusion + GRU + new heads. Stage 2: unfreeze only the last stage of each encoder at ~10× lower LR, keep only if validation improves. Frozen BatchNorm stays in eval mode. | Proposed (Raj's plan, refined) |
